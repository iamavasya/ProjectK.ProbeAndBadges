# Формат каталогу v2: як край додає свої вмілості й вимоги

Каталог — це zip з одним файлом `catalog.json` і текою `images/` поруч:

```
prague.zip
├── catalog.json
└── images/
    ├── cz-istoriia-ukraintsiv-u-chekhii-i.svg
    └── ...
```

Надсилати можна не весь каталог, а лише те, що край додає або змінює. Готовий приклад:
[examples/krai-contribution](examples/krai-contribution/catalog.json).

## Загальні правила

* **id** пишеться латиницею малими літерами, через дефіс: `cz-istoriia-ukraintsiv-u-chekhii-i`.
  Своїм новим записам край дає префікс свого коду (`cz-…`). Після публікації id не змінюється,
  бо за ним Лілейка зберігає, хто що здобув.
* **Код краю** складається з 2–3 латинських літер: `ua`, `pl`, `cz`, `de`, `us`, `ca`, …
  Він стоїть у `source.krai` один раз на весь файл.
* **Улади**: `upp` (пташата), `upn` (новацтво), `upyu` (юнацтво), `usp` (старші пластуни),
  `ups` (сеніори).
* **Статус**: `approved` (затверджена), `trial` (апробаційна), `retired` (виведена з ужитку).
  Нові вмілості краю зазвичай починають з `trial`.
* **Тексти** пишуться в markdown: `**жирний**`, `*курсив*`, підпункти рядками з `- `.
* **Зображення**: `.svg` (найкраще), `.png`, `.webp` або `.jpg`, до 2 МБ. Назва файлу латиницею
  без пробілів. SVG без скриптів і без посилань на зовнішні файли: експорт з Illustrator
  варто пропустити через [svgo](https://jakearchibald.github.io/svgomg/).
* Невідоме поле, наприклад помилка в назві (`requirments`), не ігнорується, а дає помилку
  перевірки.

## Вмілість (`badges`)

| Поле | Обов'язкове | Що це |
|---|---|---|
| `id` | так | див. вище |
| `title` | так | «Історія українців у Чехії I» |
| `family` | ні | спільний id для рівнів I, II, III однієї вмілості |
| `level` | ні | 1–5 |
| `categories` | бажано | id спеціалізацій: `zahalni-vmilosti`, `mystetska`, `sportyvna`, … (повний перелік: `GET /v1/categories`) |
| `ulady` | бажано | `["upyu"]` |
| `krai` | ні | за замовчуванням `source.krai` |
| `status` | ні | за замовчуванням `approved` |
| `images.color`, `images.bw` | бажано | назви файлів з `images/`; ч/б показується, поки вмілість не здобута |
| `prerequisites` | ні | id вмілостей, які треба мати спершу |
| `requirements` | так | список `{ "id": "1", "text": "…" }`; id — номер пункту |
| `instructorRequirements` | ні | вимоги до інструктора |
| `author` | ні | хто розробив |
| `updatedOn` | ні | дата останньої зміни тексту, `рррр-мм-дд` |
| `notes` | ні | нотатки для редакторів; людям не показуються |

## Проба (`probes`)

`id`, `title`, `ulad`, `order` (порядок показу), `sections` (розділи з `code` (А, Б, В…),
`title`, `points`) і `points` (точки поза розділами). Точка — це `{ "id": "…", "text": "…" }`.
Id точки унікальний серед усіх проб.

## Відзначення й відзнаки (`awards`)

`id`, `group` (`upyu-vidznachennia`, `kv`, `zb`, `lsh`, `shb`, …), `title`, `ulad`, `level`,
`images`, `description`, `requirements`.

## Доповнення краю до чужого запису (`overrides`)

Коли край хоче додаткову вимогу до загальної вмілості чи ще одну точку проби, він не копіює
запис, а надсилає доповнення. Його бачать лише люди цього краю, а решта бачить запис як є.

> Зараз доповнення зберігаються й перевіряються, але API їх ще не показує: запит за краєм
> віддає лише записи цього краю. Механізм буде переглянуто.

| Поле | Що це |
|---|---|
| `krai` | свій код краю |
| `target` | `badge:<id>`, `probe:<id>` або `award:<id>` |
| `addRequirements` | нові пункти вимог; id з префіксом краю: `cz-1`, `cz-2` |
| `removeRequirements` | id пунктів, які для краю не діють |
| `addPoints` | нові точки проби: `{ "section": "А", "id": "cz-probe-1-a-1", "text": "…" }` |
| `removePoints` | id точок проби, які для краю не діють |
| `title` | інша назва для краю |
| `hidden` | `true`, щоб край узагалі не бачив цей запис |
| `note` | пояснення для редакторів |

## Як перевірити до надсилання

У адмінці «Завантажити zip» спершу показує звіт перевірки і лише потім щось змінює. Офлайн з
репозиторію:

```bash
dotnet run --project tools/ProjectK.Catalog.Cli -- validate prague.zip --against catalog
```
